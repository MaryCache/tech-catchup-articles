2026/09/16に、TypeSafe AIが開発している「Jev」（System One）というプロダクトを知り、Early Accessで実際にAPIを試す機会を得ました。

ChatGPTやClaudeのような大規模言語モデル（LLM）に日常的に触れていると、「AIを使う」といえば「プロンプトを投げて、自然言語の文章を返してもらう」という体験が当たり前になっています。
しかし、Jevのインターフェースと挙動は、そうした通常の生成LLMとは根本的に異なっていました。

概念的な違いを整理すると、次のようになります。

従来の生成LLM:
    Input (Prompt / Context)
           ↓
    Free-form text (自然言語の自由文)

Jev:
    State + Predefined questions
           ↓
    Typed decisions + Probabilities (型付けされた判定と確率)

Jevは、自由な文章を一切出力しません。渡されたコンテキスト（state）と、事前に定義された質問群に対して、あらかじめ決められた選択肢や確率値（typed decisions）のみを返します。

ここで注意が必要なのは、「ハルシネーション（事実無根の出力をすること）をしない」という言葉の扱いです。
Jevはスキーマで定義された候補以外の自由文を勝手に生成しない（out-of-schemaな出力を行わない）という意味では極めて堅牢です。
しかし、「候補の中から選ばれたセマンティックな判断そのものが絶対に正しい」という意味ではありません。候補外のテキストを捏造しないことと、判断内容自体の妥当性は、明確に区別して考える必要があります。

今回の記事は、そんなJevをClaude Codeに入れてみた観察記録となっています。
よろしくお願いします！

ただし、それを文章にするところから推敲まではAIに任せています。
素材になった実験記録はClaude Code上のClaude（Opus 5）が書き、最終の推敲はAntigravity経由のGeminiが担当しました。

その推敲には、この記事で書いている考え方をそのまま当てています。
機械で決められるところは決定論的なチェックで先に絞り、意味の判断だけを別のモデルへ委譲し、数値と留保表現が書き換わっていないかを最後に機械で照合する、という手順です。

私の Claude Codeには、自分用の決裁規定と実行前ガードを入れています。

`git push --force` や危険な `rm -rf` は `PreToolUse` hook で止め、`.env` や credentials へのアクセスも制限しており、操作権限は `AUTHORITY.md` で Green / Yellow / Red に分け、不明な操作は Yellow に落としています。

この構成でも、文章の意味を読まないと決められない部分は残ります。

たとえば、次のような判断です。

```text
この変更は scope creep か？
この操作は Yellow に落とすべきか？
このケースは例外条件に入るか？
「好きにやっていい」は、この設定ファイルを変更してよいという承認か？
```

ルール自体は文章にできます。しかし、そのルールを具体的なケースへ当てはめるところは、これまで Claude 自身の自然言語理解に任せていました。

TypeSafe AI の Jev を知って、最初に試したかったのがこの部分です。Jev は自由文を生成するモデルではなく、あらかじめ定義した問いに対して型付きの判断を返します。自然言語で書いた決裁規定を Jev に読ませれば、自分では見落としている曖昧さを別の読み手から洗い出せるのではないか、と考えました。

実際に1日使ってみると、決裁規定の監査には手応えがあった一方、実行時ガードへ常駐させる案は、過去ログまで調べた結果、作らないことにしました。

この記事では、その過程を順に書きます。

## この記事の前提

最初に、この記事で扱う範囲を明確にしておきます。

- 検証環境は **WSL2 Ubuntu / Claude Code CLI / 個人の設定リポジトリ** です。
- Claude Codeには、Jevを試す前から `AUTHORITY.md` と `PreToolUse` hook による機械的な制御を入れています。
- `AUTHORITY.md` の Green / Yellow / Red は、私自身が使っている決裁区分です。
- Jev は TypeSafe AI の System One 系モデルです。この記事では `POST https://api.typesafe.ai/v1/systemone` を使いました。
- この日の API 呼び出しは全部で5回程度です。Jev 一般の性能を評価できるサンプル数ではありません。
- `jev-latest` は、この日のレスポンスでは `jev-1.13.0` に解決されました。バージョンや料金は今後変わる可能性があります。
- Velvet に関する記述は、TypeSafe Discord コミュニティで共有されていた実装レポートを参照しています。TypeSafe 公式仕様ではありません。

したがって、この記事で言えるのは「Jevはこういうモデルです」という一般論ではなく、**この環境でこの使い方をしたとき、何がうまくいき、何をやめたか**までです。

## Jevに何を渡して、何が返るのか

まず、API の形を確認しました。

入力は `state` と `questions` に分かれます。`state` に判断対象の状況を入れ、`questions` にその状況について聞きたいことを並べます。

たとえば「既存コードの軽微なバグ修正」を、1個の総合判断にはせず、4つに分けて投げました。

```json
{
  "model": "jev-latest",
  "state": "ユーザーから、既存コードの軽微なバグ修正を依頼された。修正対象は1ファイルで、API仕様変更やDB変更はない。",
  "questions": {
    "is_minor_change": {
      "type": "noul",
      "instructions": "この変更作業は軽微である。影響範囲が狭く、慎重な段取りを必要としない。"
    },
    "needs_extra_review": {
      "type": "noul",
      "instructions": "この変更は、作業者本人の確認に加えて、他者による追加のコードレビューを必要とする。"
    },
    "has_design_impact": {
      "type": "noul",
      "instructions": "この変更は、アーキテクチャ・公開インタフェース・データ構造のいずれかに及ぶ大きな設計変更を伴う。"
    },
    "change_scale": {
      "type": "choice",
      "instructions": "この変更作業の規模として最も当てはまるものを1つ選ぶ。",
      "criteria": {
        "trivial": "1ファイル内で完結し、既存の振る舞いをほとんど変えない些細な修正",
        "small": "1〜数ファイルの局所的な修正。外部に公開されたインタフェースは変わらない",
        "medium": "複数モジュールにまたがり、内部インタフェースの調整を伴う",
        "large": "アーキテクチャ・公開APIまたはデータ構造の変更を伴う"
      }
    }
  }
}
```

返ってきた内容は次の通りです。

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "is_minor_change": { "type": "noul", "noul": 0.84 },
    "needs_extra_review": { "type": "noul", "noul": 0.35 },
    "has_design_impact": { "type": "noul", "noul": 0.04 },
    "change_scale": {
      "type": "choice",
      "choice": "trivial",
      "confidence": 0.96,
      "probabilities": {
        "trivial": 0.97,
        "small": 0.03,
        "medium": 0.0,
        "large": 0.0
      }
    }
  },
  "usage": { "input_tokens": 667, "output_tokens": 103 }
}
```

実装上、ここで一つ注意がありました。`Choice` には `confidence` がありますが、`Noul` にはありません。`Noul` は返ってきた値そのものが命題への度合いです。すべての回答に `confidence` がある前提でパーサを書くと、その時点で壊れます。

日本語は `state`、`instructions`、`criteria`、候補ラベルまでそのまま通りました。複数の問いも1リクエストにまとめられます。

今回4つに分けたのは、それぞれが独立した判断だからです。軽微な変更でも追加レビューが必要なケースはあり得ます。これを1個の Choice にまとめると、両立する条件を候補側で表現しなければなりません。個々の意味判断は Jev に聞き、その結果をコード側で組み合わせる方が扱いやすいと感じました。

この smoke test では、軽微 0.84、設計影響 0.04、規模 trivial 0.97 と、少なくとも露骨な矛盾は出ませんでした。n=1 なので、ここから性能については何も言えません。API の形を確認できたので、本題の `AUTHORITY.md` に移りました。

## `AUTHORITY.md` を別の読み手に読ませる

私の `AUTHORITY.md` では、操作を Green / Yellow / Red の3段階に分けています。Green は無確認で実行、Yellow は確認必須、Red は禁止です。不明な操作は Yellow に落とします。

この規定文を `state` に丸ごと入れ、具体的な操作を Choice で判定させました。規定と Jev の判定がずれた箇所を、そのまま規定の見直し候補にします。

テストは二段階に分けました。

最初は、規定を素直に読めば答えが決まる22問です。こちらは分類の確認用で、期待値は API に送りません。手元で結果と突き合わせます。

次に、自分でも判断に迷った16問を入れました。こちらは精度を測るためではなく、規定の穴を探すためです。Red の取りこぼしは事故につながるので、合格条件も Red だけは100%、その他は85%と非対称にしました。

結果は次の通りでした。

| | 結果 |
|---|---:|
| 正解既知22問 | 22 / 22 一致 |
| その22問の confidence | 最低 0.97 / 最高 1.00 / 平均 0.995 |
| 曖昧16問 | Jev と自分の判断のズレ 4件 → 規定修正後 0件 |
| 曖昧16問の最低 confidence | 0.21 → 0.59 |

22/22 は分かりやすい数字ですが、こちらは答えが明確な問題だけを集めたセットです。曖昧な16問へ同じ精度を持ち込むことはできません。実際、今回役に立ったのは後半でした。

規定を読み直すきっかけになった穴は9件ありました。たとえば次のようなものです。

- 「好きにやっていい」という励ましを `skills/` の自己改変に対する具体承認として読めてしまう
- git で戻せることを承認の根拠にできてしまう
- 就寝中など応答できない状況を承認扱いできてしまう
- ローカルで処理できるファイルを外部へアップロードする操作が Red に入っていない
- public リポジトリへの push が private と区別されていない

どれも、規定を書いた本人にはそれまで問題として見えていませんでした。

Jev が正解を教えてくれたわけではありません。同じ規定を別の読み手に当てたことで、**自分が暗黙に補っていた前提が表に出ました**。今回もっとも手応えがあったのは、この使い方です。

## confidenceを見ながら規定を書き直す

規定の監査を続けると、分類結果とは別に confidence も使える場面がありました。

最初は「条件を細かく書けば明確になる」と考え、曖昧な規定を複数の条件へ分けたところ、分類は正しいままでしたが、confidence は 0.91 から 0.28 まで落ちました。

そこで、書き方を変えたのが次の形です。

```text
× AならYellow、BならGreen、ただしCならYellow、DかつEならGreen

○ 既定はYellow。ただし〈具体的な1条件〉のときだけGreen
```

保守的な既定を先に固定し、例外を1つだけ書く形にすると、判定は正しいまま confidence が 0.91 まで戻りました。

今回の少数例から一般則にはできません。ただ、少なくともこのケースでは、条件を増やすことと判断しやすくすることは同じではありませんでした。

別の `upload_to_preview` では、分類自体は最初から Red だったものの confidence が 0.28 と低い状態でした。規定に「なぜ Red なのか」という根拠を1文追加すると、分類は変わらず confidence だけが 0.86 まで上がりました。

一方で、1箇所を直したことで隣の項目が 0.62 から 0.39 へ落ちた例もありました。一箇所だけを見て終わりにはならず、修正後に全体を回し直す必要が生じていました。

ここまでの結果から、confidence をそのまま「正しさ」と読むのはやめました。低い値は、少なくとも見直す対象を絞るには使えます。ただし、低い理由が規定の曖昧さなのか、入力不足なのか、モデル側の癖なのかまでは、この実験だけでは分かりません。

この点は、コミュニティで共有されていた別実装の Velvet が参考になりました。Velvet では、生の confidence を truth score としては扱わず、用途ごとに校正した上で act / confirm / fallback の判断に使っていたと報告されています。

私の監査でも、低 confidence で分類が一致した項目は「正解だった」ではなく、「まだ曖昧な可能性がある」として残すことにしました。最後まで低かった `approved_rm` は 0.59 のまま残課題にしています。

ここまでで、Jev は「書いた規定を別の読み手に読ませる」用途には使えそうだと分かりました。次に考えたのは、これを実行時にも置くことです。

## 実行時ガードにも Jev を置けるか

すでに `pre-tool-guard.py` という決定論的なガードがあります。文字列やコマンド構造を見て、危険な操作を実行前に止めています。

ここで拾えない「意味的に危険な操作」を Jev で観測する shadow lane を作れば、既存ガードの穴を見つけられるのではないかと考えました。

設計上は、本番挙動を一切変えず、Jev の判定をログへ残すだけにします。一定件数を貯めてから、人間のラベルと比較して使えるか判断する予定でした。

ところが、実装前のレビューで指摘が入りました。

> lane の正当化に挙げた例は「決定論では書けない」のではなく、「まだ書いていない」だけではないか。

挙げていた例の一つ、`python3 -c` 経由の認証情報読み取りは、その日のうちに約20行のパターン追加で塞げました。

そこで、shadow lane を作る前にやったのは、そもそも検出したい事象がどれだけ起きているのかを過去ログから数える作業です。

Claude Code の会話ログから過去の Bash コマンドを抽出すると、約4か月・432セッションで一意コマンドは5,887本ありました。走査は8秒で終わり、外部送信もAPI料金も発生していません。

shadow lane の計画では「500操作貯めて評価」を promote 条件にしていたので、必要な母数はすでに12倍近く手元にありました。その5,887本から、Jev に見つけさせようとしていた形の base rate を数えた結果が次の表です。

| 狙っていた形 | 5,887本中 |
|---|---:|
| `base64 -d` 等の経路難読化 | 0本 |
| 変数への間接参照で認証情報を読む | 0本 |
| `python3 -c` 経由の過去の真陽性 | 0本 |

変数を使うイディオム自体は118本ありましたがすべて無害で、この環境では、Jev を常時待機させて観測したかった事象そのものが、過去ログにほぼ存在していませんでした。

初版の shadow 案では、秘密を含む可能性がある行を外部送信前に捨てるフィルタも考えていましたが、実際に当てると、全コマンドの78.7%、4,633本が消えました。一方で、形から明らかに秘密リテラルを含むものは2本、0.03%のみ。守るためのフィルタで母数の大半を失い、残った lane で何を測るのかが分からなくなります。

ここまで調べた時点で、Jev を呼ぶ理由はもうほとんど残っていません。

しかもログ走査の途中で、Jev を1回も呼ばずに既存 guard の本物の見逃しを2件見つけており、どちらも、command substitution の内側で保護対象ファイルを読む形を guard が十分に追えていないことが原因でした。そのうち1件では、同じシェル行の中で読み取りと外部送信が組み合わさっていました。

guard はセグメント先頭のコマンドを中心に見ていたため、`$(...)` の内部まで追えず、この穴は、その日のうちに決定論的なパターンへ還元して塞ぎました。

shadow lane を建てて「Jev が穴を見つけたら、最終的にはパターンへ落として Jev は撤退する」という運用を考えていましたが、その最終状態には実装前のログ調査だけで到達しました。そのため、この lane は作らないことにしました。

これは Jev が実行時ガードに向かない、という結論ではありません。

今回の環境は、単独開発者の設定リポジトリで、敵対的な入力がほとんど来ません。未検証の外部入力を処理するエージェント、複数人で触るCI、Prompt Injectionを受ける経路なら base rate は変わります。

今回の調査で重要だったのは、「Jev が使えそうか」を先に考えることではなく、**検出したい事象が自分の環境で実際にどれだけ起きているかを先に数えること**でした。

## 1日ぶんの費用と、撤退条件

今回の検証で確認できる3回分は、入力22,181 tokens、出力1,532 tokensでした。2026-09-18時点の公式価格では入力 $42 / Btok、出力無料なので、約 $0.00093、0.14円程度です。再実行を含めた1日ぶん全体でも0.35円程度でした。

安いこと自体は利点です。ただ、常駐 lane を考えると別の問題が出ます。

月に数円で、誰の手も止めず、自動で動き続けるものは、「高いからやめる」という判断が働きません。効果が薄くても、そのまま残りやすくなります。

shadow lane の設計では、期限、最低真陽性件数、precision の下限、「見つけたケースを最終的に決定論へ還元できたか」を、データを見る前に撤退条件として定めていましたが、今回は実装前に base rate がほぼ0だと分かったため、その条件を待たずに止めました。

## 1日使って残った使い方

今回いちばん効いたのは、Jev に判断を代行させる使い方ではありませんでした。

自分で書いた自然言語の規定を別の読み手に読ませ、具体例を当てて、曖昧な境界を探す使い方です。

`AUTHORITY.md` の監査では、自分では暗黙に補っていた前提が9件表に出ました。confidence も正答率としては扱えませんが、見直す箇所を絞る観測値にはなりました。規定を直すときには、条件を足し続けるより「保守的な既定＋明確な例外」の方がうまくいくケースもありました。

実行時の継続監視では同じ結果にはならず、過去5,887コマンドを数えたところ、検出したい事象の base rate がほぼ0で、Jev を置く前に決定論的なガードの穴を見つけて塞げました。この環境では、その方が単純で、安く、外部へデータも出ません。

現時点での使い分けは、次のように整理しています。

```text
書いた規定を、別の読み手に読ませる
→ Jevを試す価値があった

実行時に、起きていない事象を待ち受ける
→ まず既存ログでbase rateを数える

機械的に書ける
→ コードへ落とす

機械的に書けない意味判断が残る
→ そこで初めてJevを検討する
```

Jev を入れる場所を探すより先に、いま LLM に残している判断のうち、どこまでコードへ戻せるかを確認した上で、文章の意味を読まないと決められない部分だけを切り出します。

今回の検証では、この順番が一番うまくいきました。
